In-store clearance

How Penny Run works

A markdown hunter for Home Depot: a droplet asks their pricing API what every product costs at each of your stores overnight, and your phone answers a barcode from that list in the aisle.

The constraint

A price only exists once you name a store

Everything below is shaped by one fact. Home Depot's API will not quote a price for an unlocalised request, and the deep markdowns belong to a single building. The same bag of mulch, asked eight ways:

So there is no list to fetch — there is only a question you can ask 4.2 million times. That is the whole job of the nightly sweep.

Overnight · on the droplet

Discovery is broad and cheap. Verification is narrow and deep.

Pricing 4.2 million products at eight stores is 34 million questions a night, which is not happening. So the sweep splits: find candidates by asking one store, then confirm the survivors at all of them.

The keyword pool was the weaker half

The seed pool was built by scraping "<term> clearance" searches, which sounds like the obvious source and measured worse than picking products at random: 1.5% of its products are on clearance against 2.9% of random sitemap products. Searching for "clearance" finds what Home Depot markets as clearance — the shallow national stuff — not a store manager emptying a pallet. The deep cuts are on things nobody thinks to search for. That is why they got cut.

In the aisle · on the phone

Scan a box, get an answer before the camera refocuses

The list is already on the phone, so a barcode is answered from local data with no network at all — which matters in the back corner of a building made of steel racking.

What the verdict actually counts

Clues stack into a score. GREEN needs five points and an anchor clue — a printed date, a "was" price, or a confirmed clearance price. YELLOW needs two. Everything else is RED.

Two signals were measured and left out. "Store only" looks like it should predict a markdown and points the wrong way — 14% among clearance items against 22% among everything else — so it shows on the row as information but scores nothing. And discontinued, obsolete and isBuryProduct are the obvious fields to reach for; across 636 products all three are always false or null.

Topology

One droplet does both jobs

Because the machine that sweeps is also the machine that serves, the nightly job writes clearance.json straight into what the web server is already handing out. No build step, no deploy, no waiting.

Failure modes

What stops bad data reaching the aisle

The expensive failure is not a crash — it is a sweep that quietly returns nothing and replaces a good list with an empty one. That has already happened once, on a GitHub runner, and it looked exactly like eight stores with nothing on clearance.

  • The probe runs first. It knocks on all three Home Depot hosts with no retries and no swallowed exceptions, so a machine that is being refused says so on the line that matters.
  • The scan will not write a collapsed run. Empty, or below 40% of the previous total, and yesterday's list keeps serving.
  • The harvest keeps the old pool if a run comes back below 60% — that is Home Depot changing their markup, not the catalogue shrinking.
  • The file is renamed into place, so a phone fetching mid-sweep gets the old list whole rather than half a new one.

Not every machine can run this. GitHub's hosted runners get 206 Generic Errors API from the pricing API for their whole address range — measured four ways, including origin and referer headers, a desktop user-agent, and Apollo client headers. All four were refused; the same code from a residential address gets 200 every time. It is the address, so no header fixes it. Check any new box with tools/checkhost.py before building on it.
